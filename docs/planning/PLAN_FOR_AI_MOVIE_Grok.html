Plan for ai-movie

1. Summary

Build a file-driven pipeline that starts from a topic, produces a narrated explainer (or hybrid short drama) script, expands it into a shot list, turns every shot into a precise programmatic scene record, renders a hand-sketched storyboard SVG that already encodes camera, pose, gaze, props and simple environment, then uses that SVG (or a derived ControlNet-ready depth/pose map) as the composition lock for an image model and finally an image-to-video model. Human gates sit only at script, storyboard approval and final cut. Everything else is unattended, idempotent and re-runnable from the project folder. The three decisions that matter most are: (1) treat the storyboard SVG as the authoritative composition contract and feed it as a first-frame or strong ControlNet reference rather than relying on text alone; (2) ship first as short vertical explainers (30–60 s) on YouTube Shorts / TikTok / Reels because the economics and approval loop are tighter and character consistency is deliberately not required; (3) keep the storyboard renderer in pure Node with zero runtime dependencies so agents and humans can both drive it deterministically.

2. Where I disagree with the decisions or the core bet

Core bet is largely correct but incomplete. Text prompts are indeed a weak way to lock camera height, foreshortening, gaze and relative scale. Programmatic composition first is the right move. However, the bet under-weights how good modern image-to-video models have become at respecting a strong first frame (Seedance 2.5, Kling 4.0, Wan 3.0, MiniMax H3 and FLUX 3 variants all treat a well-composed still as near-sacred). The pipeline should therefore optimise the storyboard → still → video path more than pure text-to-video. Pure text-to-video remains a fallback for abstract B-roll only.

Character consistency not required. I agree for the first product (faceless explainer). For short character drama later it becomes a liability; the architecture should leave a clean hook for reference-image sets and identity locks without forcing them now.

Hand-sketched look must be preserved but not romanticised. The SVG mannequin is a control signal, not the final aesthetic. The generation stage should be able to render photoreal, graphic-novel, or clean 2.5-D styles from the same scene record. Treating the sketch itself as the final look limits platform appeal and makes lighting/environment work harder than necessary.

Three human approvals are correct in principle but the middle one (storyboard) should be cheaper. Approve a low-resolution contact sheet of all frames plus a one-line “what this shot must convey” rather than pixel-perfect SVGs every time. Agents can auto-reject frames that fail joint-range, interpenetration or camera-framing heuristics before the human ever sees them.

File-only stage communication is excellent and I would keep it religiously. It is the only way agents, humans and future replacements stay interchangeable.

3. Answers to the open questions

1. Format: narrated explainer over visuals, or short character drama? Or both, and in what order?

Recommendation: Start exclusively with narrated explainer (faceless or with generic silhouetted figures). Add short character drama as phase 3 once the composition → generation loop is reliable.

Reasoning: Explainers have lower creative risk, no need for identity consistency, cheaper per-second generation (can reuse B-roll styles), and clearer success metrics (watch time, retention). Drama requires reliable multi-figure interaction, consistent wardrobe/face across cuts, and better lip/gesture sync; those are still expensive failure modes in November 2026. Order: explainer first, then hybrid “explainer with one recurring illustrative character”, then pure short drama.

Alternatives: Pure drama from day one (higher risk, slower iteration). Dual-track (two parallel pipelines) — rejected because it doubles the hard problem of scene-record generation.

2. How should a storyboard frame drive generation: as a reference/control image fed to the model, or converted into a precise text shot description? Which current models support which route?

Recommendation (November 2026, verify): Primary path = render SVG → convert to depth + OpenPose-style skeleton + optional Canny → feed as ControlNet / spatial condition into an image model to produce a high-quality still → feed that still as first frame (and optionally last frame or keyframe) into an image-to-video model. Secondary path = auto-generate a dense text shot description from the scene record and use it as the prompt (or as a parallel conditioning signal). Never rely on text alone for composition-critical shots.

Current support (verify):

  • Image models with strong ControlNet / spatial control (OpenPose, depth, lineart): still widely available via ComfyUI / fal / local (SDXL, Flux variants, Z-Image, etc.).
  • Image-to-video that respects first frame tightly: Seedance 2.5 (ByteDance), Kling 4.0 (up to 10 keyframes), Wan 3.0, MiniMax H3 / Hailuo, FLUX 3 Max, Gemini Omni Flash family. Many accept additional reference images for style or identity.
  • Pure text-to-video is usable for abstract or establishing shots but loses the composition lock the whole pipeline is built around.

Alternatives: Text-only (cheaper, less controllable). Direct video ControlNet (rare and less mature). IP-Adapter + pose (useful later for mild identity).

3. Text-to-speech provider that returns word-level timings

Recommendation (November 2026, verify): Cartesia Sonic (strong word timestamps over SSE/WebSocket, 44 languages, good latency) or ElevenLabs (excellent quality, word timestamps available, broad language/voice library). Inworld also returns word + character timestamps and visemes. Prefer the one that gives clean JSON timestamps out of the box and has a stable Node SDK.

Reasoning: Word-level timings are non-negotiable for burn-in captions and for any future lip-sync or gesture emphasis. Quality and emotional range matter more than absolute cheapest price for a publishable product.

4. Target platforms, aspect ratios and lengths

Recommendation: Primary: 9:16 vertical, 30–60 s (YouTube Shorts, TikTok, Instagram Reels). Secondary: 16:9 60–120 s for YouTube long-form once the pipeline is stable. Always produce both aspect ratios from the same scene records by changing only the camera frustum and framing rules.

Reasoning: Vertical short-form has the highest distribution leverage and the shortest feedback loop. Platforms require AI labels for realistic generated content (YouTube, TikTok, Meta — verify current wording); the pipeline must emit the label metadata and an on-screen disclosure option.

5. A realistic per-video budget, and how to keep within it

Recommendation: Target $3–8 all-in for a 45 s explainer in the first year (script LLM + image stills + 4–8 video clips of 4–8 s + TTS + music + assembly). Stretch goal under $4 once caching and model selection mature.

How: (a) Generate one high-quality still per shot, then 4–6 s of video from it rather than long continuous generations. (b) Prefer mid-tier image-to-video models that still respect the first frame (Gemini Omni Flash / cheaper Seedance / Kling tiers when quality allows). (c) Aggressive caching of scene records, SVGs and approved stills. (d) Human approval before any video tokens are spent. (e) Local or cheap open models for non-critical B-roll. Prices move monthly — re-benchmark quarterly (verify).

6. Narration language handling

Recommendation: Script and shot list authored in English first (largest model capability surface). TTS in the target language. For non-English, run a dedicated translation + cultural adaptation pass after the English script is approved, then re-time the voice. Captions always generated in the spoken language; optional secondary caption track in English. Scene records and camera language stay language-agnostic.

4. Architecture

Modules

  • orchestrator — thin Node/TypeScript CLI + simple state machine that walks the project folder, detects which stage files are missing or stale, and invokes the next agent or tool.
  • script — LLM agent that turns topic + constraints into structured script JSON.
  • shot-list — expands script into timed shots with camera intent and visual description.
  • scene-record — the hard core: natural-language shot → validated scene record JSON (figures, props, environment, lights, camera).
  • storyboard-renderer — existing pure-Node SVG renderer, extended.
  • still-gen — SVG/depth/pose → image model → approved still.
  • video-gen — still (+ optional motion prompt) → image-to-video clips.
  • voice — TTS with word timings + caption generation.
  • music / sfx — lightweight library or generative bed + simple ducking.
  • assembly — FFmpeg-based timeline that consumes clips, audio, captions, produces final masters + platform variants.
  • publish — metadata, AI labels, thumbnails, optional auto-upload hooks.

5. Each stage in detail

Script

Inputs: topic.md, constraints (duration, tone, platform, must-include facts).
Outputs: script.json.
How: Structured LLM call with few-shot examples of good short explainers. Enforce section timing budgets and a single clear hook in the first 3 s.
Failure modes: vague visuals, over-long narration, missing CTA. Retry with tighter length constraint + “show don’t tell” reminder.
Cost: cents.
Acceptance: human reads it aloud against a timer; every section has a concrete visual intent.

Shot list

Inputs: approved script.json.
Outputs: shotlist.json.
How: LLM expands each section into 1–4 shots, assigns rough durations that sum to target, proposes camera language and figure count. Deterministic post-pass normalises IDs and timing.
Failure modes: too many cuts, impossible camera moves, narration/visual mismatch. Auto-flag shots whose description cannot be realised with current renderer capabilities.
Cost: low.
Acceptance: total duration within 10 % of target; every shot has a one-sentence “must convey”.

Storyboard / scene-record generation (the hard stage)

Covered in section 6. Output is scenes/*.json + *.svg. Human approves a contact sheet.

Generation (still then video)

Inputs: approved scene records + SVGs.
Outputs: stills and short video clips.
How: (1) SVG → depth + pose maps (or direct raster). (2) Image model conditioned on those maps + style prompt derived from script. (3) Human or vision-model triage of stills. (4) Image-to-video from approved still + short motion prompt extracted from camera + figure intent. Prefer 4–6 s clips; extend only when necessary.
Failure modes: pose drift, extra limbs, ignored camera, style collapse. Retry with stronger ControlNet weight or different seed; fall back to text+first-frame only if spatial control fails.
Cost: dominant line item. Gate behind still approval.
Acceptance: still matches scene record composition on a simple overlay test; video keeps the same framing for the first 80 % of its length.

Voice and captions

Inputs: script narration text + timings target.
Outputs: wav + word timings JSON + SRT/VTT.
How: TTS provider that returns word timestamps. Optional SSML/emotion tags from script. Captions generated directly from timings; style sheet for safe-area vertical video.
Failure modes: mispronunciation of technical terms, timing drift. Dictionary / IPA overrides; human listen pass only on final assembly if needed.
Cost: low–medium.
Acceptance: word error rate on a known script < 1 %; captions never overflow safe area.

Music

Inputs: mood tags from script, duration.
Outputs: bed track + simple volume automation.
How: curated library first (cheapest, most controllable); generative music only if no good match. Duck under narration via side-chain or pre-computed envelope.
Cost: near zero if library; low if generative.
Acceptance: no frequency clash with voice; energy matches section intent.

Assembly

Inputs: all clips, voice, captions, music, timeline.json.
Outputs: master files in required aspect ratios + platform packages.
How: FFmpeg or Remotion-style renderer driven by declarative timeline. Handles transitions (hard cut default, optional dissolve), caption burn-in or soft subs, loudness normalisation, AI-label slate if required.
Failure modes: A/V sync drift, wrong aspect crop. Deterministic re-render from timeline.json; checksums on inputs.
Cost: compute only.
Acceptance: exact duration match, peak loudness within platform specs, captions legible on phone.

Publishing

Inputs: masters + meta.
Outputs: uploaded assets or ready-to-upload folder + disclosure JSON.
How: generate titles, descriptions, chapters, hashtags; apply required AI disclosure labels; optional thumbnail from key still. Manual upload in v1; API hooks later.
Acceptance: checklist of platform requirements ticked.

6. The hardest problem: natural-language shot → valid scene record

This is the make-or-break stage. Treat it as a constrained code-generation + validation loop, not free-form creative writing.

Concrete method:

  1. Pose library first. Every shot description is matched (embedding + keyword) against the 18+ reference scenes. Start from the nearest named pose or a composition of two, then apply deltas for gaze, reach and body profile.
  2. Structured extraction. LLM call with a strict JSON schema (figures[], camera, environment preset, props, lights). Few-shot on the existing hand-written scene records. Force the model to choose from the known profile and hand/pose vocabularies.
  3. Renderer as oracle. Immediately run the scene record through the storyboard renderer. Collect every warning (joint clamp, unreachable target, extreme foreshortening, out-of-frame, interpenetration heuristic). Feed the warnings + the SVG back to the LLM in a correction turn: “These joints were clamped; adjust the pose or the reach target.”
  4. Multi-figure & environment. Start simple (one figure + cuboid props). Add a second figure only when the description requires interaction; use relative positioning constraints (“2 m to the left of figure A, facing her”). Environment starts as named presets (suburban_site, interior_office, balcony) that expand into cuboids + props.
  5. Automatic quality gates before human.
    • All joints within limits (or explicitly marked acrobatic).
    • Gaze target projects inside the frame or is intentionally off-screen.
    • At least 60 % of each figure’s bounding box inside the camera frustum.
    • No two solid props intersecting (simple AABB or capsule checks).
    • Camera not inside geometry.
  6. Human judgement. Contact sheet of SVGs + the original shot description + the “must convey” line. Human can accept, reject, or edit the JSON directly (the renderer is fast). Accepted records become additional few-shot examples, closing the loop.
  7. Judging quality. Automatic: the gates above + a cheap vision model that scores “does this SVG match the shot description?” on a 1–5 scale. Human: cinematic criteria (clear silhouette, readable action, intentional camera height, balanced negative space). Never let an automatic score fully replace the human gate at this stage.

7. Storyboard renderer roadmap

  1. Immediate (week 1–2): multi-figure support, basic interpenetration warnings, simple environment cuboids and ground plane, directional light + soft contact shadows, camera safe-area guides for 9:16 and 16:9. Deterministic tests for the 18 reference scenes.
  2. Next: named environment presets that expand to geometry, prop library expansion (panels, tools, vehicles as simplified meshes), better hand shapes, clothing silhouettes that read at small size, export of depth and OpenPose-style skeleton images directly from the same scene record.
  3. Then: simple animation curves between two scene records (for motion prompts or in-between stills), lighting intensity/colour temperature controls, occlusion ordering fixes.
  4. Later: optional more sophisticated mannequin (muscle masses, better foreshortening) only if the ControlNet path still needs it; keep the core pure-Node and dependency-free.

Order is driven by what unblocks the still-generation stage first.

8. Testing strategy

  • Renderer: golden SVG files for every reference scene + a growing set of multi-figure and environment cases. Pixel or perceptual hash diff; any change requires explicit golden update. Joint-limit and IK unit tests independent of drawing.
  • Scene-record generation: hold-out set of shot descriptions with known-good records. Measure schema validity, warning count, and human accept rate. Regression: every previously accepted record must still round-trip through the renderer without new errors.
  • End-to-end: three fixed topics that produce a full video; cost, duration and human approval rate tracked. Snapshot the project folder after each stage for replay.
  • Visual: still vs scene-record overlay test (pose keypoints projected into the still must land near the mannequin joints). Video first-frame vs still SSIM or LPIPS threshold.
  • Non-visual: caption timing accuracy, loudness, aspect-ratio crops, presence of required AI disclosure metadata.

9. Phased delivery

Phase 0 – smallest end-to-end (2–3 weeks): manual scene records for a 30 s explainer, existing renderer, one image model + one image-to-video model, Cartesia/ElevenLabs voice, FFmpeg assembly. Produces a real publishable vertical video. Proves the composition lock works.

Phase 1 – close the loop: automatic scene-record generation with renderer feedback, still approval gate, cost tracking, contact-sheet UI (even if CLI + browser).

Phase 2 – production hardening: multi-figure + environments, dual aspect ratio, music, robust retries, project-folder orchestrator, basic publish checklist.

Phase 3 – drama capability: identity reference sets, multi-shot character continuity helpers, longer timelines, optional lip-sync.

Phase 4 – scale: agent-only runs with higher auto-accept thresholds, model routing by budget/quality, analytics on retention vs composition metrics.

10. Risks and mitigations

  • Scene-record quality plateaus: keep humans in the loop longer; invest in better few-shot and warning feedback; grow the pose library from every accepted frame.
  • Model price or quality shifts: abstract the still and video providers behind a thin interface; re-benchmark monthly; keep a local/open fallback path.
  • Platform AI-label and monetisation rules change: always emit disclosures; prefer styles that are clearly illustrative when rules tighten; monitor YouTube/TikTok/Meta policy pages.
  • Composition lock fails on video: fall back to stronger first-frame models or shorter clips; add keyframe support when available (Kling-style).
  • Cost blow-outs: hard budget per project; still approval before video spend; cache everything.
  • Agent non-determinism: scene records and renderer are deterministic; only creative LLM steps are stochastic and are always human-gated or auto-validated.

    Description: 30–50 diverse shot descriptions with human-validated target records; used for regression of the generator.
    Acceptance criteria: Generator accept rate measurable and tracked over time.
    Tests: The set itself.
    Depends on: 11–13.

  30. Title: Vision-based still quality scorer
    Description: Cheap model that scores still vs scene-record alignment and flags obvious defects before human review.
    Acceptance criteria: High precision on known bad stills; low false-positive rate.
    Tests: Labelled mini-set.
    Depends on: 15.

  31. Title: Caching layer
    Description: Content-addressed cache for SVGs, depth maps, stills and video clips so re-runs of unchanged stages cost nothing.
    Acceptance criteria: Second run of an unchanged project spends $0 on generation.
    Tests: Cache hit rate on fixture.
    Depends on: 17, 22.

  32. Title: Simple web review UI (optional but high leverage)
    Description: Local or lightweight hosted page that shows contact sheet, stills, and final video with approve/reject buttons that write the approval files.
    Acceptance criteria: Non-engineers can perform the three gates without touching JSON.
    Tests: Usability on a real project.
    Depends on: 14, 24.

  33. Title: Model routing and budget guardrails
    Description: Config that chooses cheaper models for B-roll and enforces a hard $ ceiling per project.
    Acceptance criteria: Project aborts cleanly before exceeding budget.
    Tests: Forced over-budget scenario.
    Depends on: 17, 22.

  34. Title: Documentation of cinematic heuristics
    Description: Short internal guide that translates common shot descriptions into camera height, lens feel and figure placement rules used by the scene-record agent.
    Acceptance criteria: New contributors can predict what the agent will emit.
    Tests: None (living doc).
    Depends on: 11.

  35. Title: Phase-1 retrospective and metrics dashboard
    Description: After first 10 real videos, record accept rates, cost distribution, common failure modes and update the pose library and few-shot examples accordingly.
    Acceptance criteria: Written report + updated few-shot set.
    Tests: None.
    Depends on: 25, 29.

This plan is deliberately opinionated toward composition control first, short vertical explainers first, and ruthless cost gating. The existing pure-Node renderer is a genuine advantage; treat it as the spine of the system rather than a temporary sketch tool.
